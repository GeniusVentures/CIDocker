## Phase Goal

**As a** CI engineer, **I want to** push and verify the AlmaLinux 8 image for `amd64` + `arm64` (and reject any 32-bit architecture), **so that** consuming CI can pull the correct architecture by tag with confidence.

> Re-expressed from the ROADMAP Phase 4 goal ("The image is verified to build and run on `amd64` and `arm64` — and only those architectures"). This is a CI/config-verification phase; the "feature" is the multi-arch verification pipeline itself, delivered as one workflow file.

<objective>
Create `.github/workflows/ci-almalinux.yml` — a separate GitHub Actions workflow that builds and pushes `ghcr.io/geniusventures/almalinux-8:latest` for `linux/amd64` + `linux/arm64` via buildx, then verifies the push: (1) a static arch-clean grep gate, (2) a multi-arch manifest inspection asserting both platform digests, (3) pull-by-tag architecture resolution checks, and (4) a QEMU-emulated arm64 runtime smoke test covering the full tool probe set.

Purpose: Automated proof that the Alma image builds and runs on exactly `amd64` + `arm64` (BASE-03, PAR-03), and that CI consumers can pull the correct architecture by tag — without touching `.github/workflows/ci.yml` (bullseye-only, per D-03).
Output: `.github/workflows/ci-almalinux.yml` (the only new artifact).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → ghcr.io registry | Build outputs cross this boundary on push; registry auth + image integrity matters here. |
| GitHub Actions runner → Dockerfile / build context | Untrusted repo content (Dockerfile, base image tag) enters the build. |
| Workflow YAML → GitHub Actions runtime | The workflow itself is repo content executed with the repo's `GITHUB_TOKEN`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Information Disclosure | docker/login-action credentials | mitigate | Authenticate with `docker/login-action@v4` using ephemeral `${{secrets.GITHUB_TOKEN}}`; no step echoes the token or any secret. |
| T-04-02 | Tampering | Build context / base image | mitigate | Build from official `almalinux:8` (validated in Phases 1–3); context via `actions/checkout@v6` of the repo's pinned commit; `context: almalinux-8` only. |
| T-04-03 | Tampering | GitHub Actions supply chain | mitigate | Pin only official `docker/*` actions at `@v4`/`@v6`/`@v7` — the same set already trusted and running in `ci.yml`. |
| T-04-04 | Elevation of Privilege | GITHUB_TOKEN scope | mitigate | Workflow-level `permissions: { contents: read, packages: write }` (least privilege, mirrors `ci.yml`); no `contents: write`. |
| T-04-05 | Spoofing | Registry identity | mitigate | `docker/login-action` authenticates as `${{github.actor}}` to `ghcr.io`; pull/inspect/smoke all reference the same authenticated `ghcr.io/geniusventures/almalinux-8:latest`. |
| T-04-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this phase (Package Legitimacy Audit: N/A) — only the already-verified official `docker/*` actions and the `almalinux:8` base image. |
</threat_model>
